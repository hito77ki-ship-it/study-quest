## 誤検出の原因：スプライトは動的にパスを組み立てていた

`app.html` の9182〜9188行に、以下の関数がある。

```js
function getHeroSpriteFor(gender, cls, state){
  // 男性戦士だけファイル名にclassが入らない命名
  if(gender==='male' && cls==='warrior') return `sprites/hero-male-${state}.png`;
  return `sprites/hero-${gender}-${cls}-${state}.png`;
}
```

`gender`（male/female）× `cls`（warrior/mage/monk/cleric）× `state`（normal/damaged/critical）の組み合わせで、**24通りのパスが実行時に生成される**。文字列としてソースに存在しないため、grepでは1件も引っかからない。

さらに `state` は飾りではなく、実際にHPで切り替わる。

```js
function getHeroState(){
  const pct = hp / max;
  if(pct <= 0)    return 'critical';
  if(pct < 0.30)  return 'critical';
  if(pct < 0.65)  return 'damaged';
  return 'normal';
}
```

**つまり `hero-*-damaged.png` `hero-*-critical.png` の16枚は、ユーザーのHPが減ったときに実際に表示される現役ファイルだった。** これらを「孤立」として削除していたら、HPが減った瞬間に画像が壊れる不具合を作り込むところだった。

監査時に「`sprites/`配下は動的生成の可能性があり削除は危険」と留保をつけていたのは正しかったが、**件数と容量を17.34MBと報告したのは不正確だった**。動的生成分を差し引いてから報告すべきだった。

## 真に未参照だったもの（8件・約4.6MB）

### A. 記事用に作られたが記事に貼られていない図解（4件・3.9MB）

| ファイル | サイズ | 想定される用途 |
|---|---|---|
| `images/hojinzei-shohizei-map.png` | 1,070 KB | `boki2-hojinzei-shohizei.html` 用と推測 |
| `images/seizo-genka-box.png` | 1,025 KB | `boki2-seizo-genka-hokokusho.html` 用と推測 |
| `images/junshisan-map.png` | 942 KB | `boki2-junshisan.html` 用と推測 |
| `images/boki3-shiwake-map.png` | 835 KB | 簿記3級の仕訳解説用と推測 |

**いずれも対応しそうな記事は存在するが、記事側に`<img>`が無い。** 図解を作ったあと、記事への挿入を忘れた状態と考えられる。

なお、これらは**1枚あたり1MB前後と非常に重い**。仮に記事へ挿入する場合は、他の図解と同様にSVG化するか、WebP変換してから貼るべきで、このまま貼ると当該記事のLCPが一気に悪化する。

### B. アプリの未実装機能用アセット（4件・約0.7MB）

| ファイル | サイズ | 状況 |
|---|---|---|
| `sprites/boss-golem.png` | 273 KB | `boss-dragon.png`のみ実装済み。ゴーレムは未実装 |
| `sprites/chest-closed.png` | 115 KB | 宝箱機能は実装されているが、**画像ではなく絵文字**（📦🎁💀）で表現されている |
| `sprites/chest-open-empty.png` | 132 KB | 同上 |
| `sprites/chest-open-gold.png` | 158 KB | 同上 |

宝箱については、`app.html` の10582行付近で `.lucky-chest-icon` の `textContent` に絵文字を代入する実装になっており、用意された画像は使われていない。**画像版に差し替える構想があったが絵文字で実装した、という経緯と推測される。**

## 提案

いずれも**表示速度には影響しない**（読み込まれていないため）。リポジトリ容量の話でしかないので、優先度は低い。

- [ ] **A群4件：記事に挿入するか、削除するかを決める。** 作った図解を眠らせているのは工数の無駄。ただし挿入する場合は必ず軽量化してから
- [ ] **B群のboss-golem：** ボス追加の予定があるなら残す。無いなら削除
- [ ] **B群のchest3件：** 絵文字実装で確定なら削除、画像に差し替える構想が残っているなら保持

**なお `app/build/` について、監査では「リポジトリにコミットされている」と報告したが、これも誤りだった。** `.gitignore` に `app/build/` は既に登録済みで、`git ls-files app/build/` は0件。ディスク上に275MB存在するが、Gitの追跡対象ではない。お騒がせした。

## 今回の反省

**「grepで見つからない＝未使用」は、JavaScriptでパスを組み立てるコードベースでは成立しない。** 今回は幸い留保をつけていたため実害はなかったが、報告した数値そのものが誤っていた。

今後、未使用アセットを報告する際は、

1. 静的な文字列検索
2. **テンプレートリテラル・文字列連結によるパス生成箇所の洗い出し**
3. 生成されうる全組み合わせの列挙と照合

の3段階を踏むこととする。
