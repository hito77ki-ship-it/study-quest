## 2. ファクトチェックリサーチ

### AdSense の低品質コンテンツ（Low-Value Content）判定について

- 「低品質コンテンツ」とは、実際の読者に対して十分な独自かつ有用な情報を提供していないと判断された状態。**内容の薄い記事（thin articles）**が代表例（AdSense Audit / Geniee）
- 一つの目安として、**サイトの過半のページが300語未満**の場合に thin content と見なされやすい。より具体的には300〜400語を下回る、詳細さや有用性に欠ける記事（HubPages / Monetiscope）
- **ただしGoogleは公式には最低文字数を定めていない。**「300語で焦点の絞られた問いに完璧に答えるページは通るが、1,500語のフィラーだらけの記事は低品質と判定されうる」——**評価軸は長さではなく質である**（AdSense Audit）
- 推奨としては1,000語以上の高品質記事を20〜25本、または800〜1,000語を15〜20本（All Are Seo Tools）

### 自社の状況との突き合わせ（誠実に評価する）

`boki2-kessan.html` は本文2,147**字**（日本語）である。日本語の1文字は英語の1語より情報密度が高いため、英語基準の「300語」に単純換算すれば十分に上回っており、**この記事単独が thin content として弾かれる水準ではない。** 記事数も約200本あり、量的な要件は満たしている。

**したがって「AdSense審査に落ちる原因がこの記事だ」と断定することはできない。** 過度な危機感を煽るのは正しくない。

一方で、上記ソースが繰り返し強調する**「評価軸は長さではなく質」**という点で、この記事には明確な弱さがある。すなわち：

- 各決算整理事項が2〜3行の要約で終わり、**具体的な数値を使った仕訳例が一つもない**（他14本のうち8本には例題がある）
- FAQセクションがなく、読者の具体的な疑問に答えていない
- 出典のない「8割」という主張がある

**「焦点の絞られた問いに完璧に答えている」とは言えない。** これが是正すべき理由である。

### 更新日表示について

構造化データと画面表示の食い違いは、CLAUDE.mdが2026-07-29に自ら明文化したルールへの違反である。**外部ソースを引くまでもなく、自社ルールに照らして不整合と判定できる。**

## 3. CEOジョブズの所見

**簿記2級の第3問。配点が最も大きく、検索需要も最大級。そこに一番薄い記事を置いていた。** これは技術的なバグではない。**優先順位の付け方の誤りだ。**

私は率直に認める。この3か月、比較記事（「AとBの違い」）を大量に作ってきた。それは検索意図が明確でCVしやすいからだ。**その結果、シリーズの背骨にあたる大論点が相対的に手薄になった。** `boki2-kessan.html` は5月9日公開のまま、7月8日に何かを触られた形跡はあるが、中身は薄いままだ。**新しいものを作るのは楽しい。既にあるものを深くするのは地味だ。私は楽しい方を選んでいた。**

「8割はカバーできます」という数字も同じ問題だ。**根拠なく数字を出すのは、読者を安心させるためではなく、書き手が言い切って気持ちよくなるためだ。** これは削るか、根拠を示すかの二択しかない。

`.td-total` / `.td-minus` については、実害がないから軽微だと言うのは違う。**`.td-total` は「使った瞬間に読めなくなるCSS」がファイルに残っている状態だ。** 未来の自分（または未来の私）が親切心でこの class を使い、ダークモードで読めなくなる。**未使用の壊れたCSSは、無害ではなく罠だ。**

更新日の不一致9本については、7月29日に自らルールを明文化したその翌日に、**遡及分がまるごと残っていることを発見した。** ルールを書くことと、既存の違反を掃除することは別の作業である。**明文化した時点で満足していた。**

「絶対に間違えなくなります」について。**私は完璧主義者だが、読者に完璧を約束はできない。** 記事を1本読んで絶対に間違えなくなる人間はいない。これは読者への誠実さの問題であり、同時にAdSenseが見る信頼性の問題でもある。

**最優先目標との関係：**
- **AdSense合格：** ①（薄さ・根拠なき数値）と④（過度な断定）は寄与する。ただし**これが不合格の主因だと断定はできない**（上記リサーチの通り、量的基準は満たしている）
- **検索上位表示：** ①は直結する。第3問は簿記2級で最大級の検索需要があり、そこに競合より薄い記事を置いていれば上がらない
- **②③は最優先目標にほぼ寄与しない。** 保守性と自社ルールの整合性のための作業である。**この2件を「SEOに効く」と装うのは不誠実なので、そう書かない**

**シンプルさの観点：** ②は純粋な削除作業（足すものがない）。③は日付1行の追加。①だけが加筆であり、ここが唯一「膨らませる誘惑」がある箇所だ。**文字数を増やすことを目的にしてはいけない。数値例とFAQを足すだけで、一般論の水増しは絶対にしない。**

**妥協点を正直に書く。**
- ①について、本来は各決算整理事項に個別記事があるのだから、`kessan` は「ハブとして各記事へ丁寧に振り分ける」役割に純化する設計もありえる。**加筆と純化のどちらが正しいかは、実際の検索順位データを見ないと決められない。** 今回は「数値例とFAQを足す」という中間的な選択をする。これは最適解である確証がない
- ②の未使用CSS削除は、`.lead` `.flow` `.formula` のように**widgets標準クラスと同名のものが含まれる。** これらは削除しても widgets 側が提供するので安全と推定されるが、`20260729-widgets標準クラスのローカル再定義スキャン.md` が `.related-*` で報告した「widgets にライトモードのベースが無く削除すると崩れる」ケースの再来を避けるため、**1件ずつ widgets 側の定義を確認してから削除する。一括スクリプトでの削除は行わない**

## 4. 提案する対応

### 案A（推奨）：3件を分離して段階実施する

**A-1. `boki2-kessan.html` の拡充（最優先）**

- 6大整理事項の各項目に**具体的な数値を使った仕訳例を1つずつ追加**（売上原価の算定・減価償却・貸倒引当金・経過勘定・有価証券・法人税等）
- **FAQセクション（3〜4問）と FAQPage JSON-LD を追加**（他14本と同じ形式に揃える）
- **会話セクション（2往復）を追加**（若葉ペルソナ。他13本と同じ `.sq-chat` 系を使う）
- **「8割はカバーできます」を修正。** 過去問の実測に基づく根拠を示せない場合は削除し、「6大整理事項が第3問の中心である」という定性的な記述に置き換える
- **一般論の水増しは行わない。** 数値例・FAQ・会話以外は加筆しない

**A-2. 効かないCSS・死にコードの整理**

- `boki2-hojinzei-shohizei.html` / `boki2-junshisan.html` から `.td-total` `.td-minus` `.td-r` を削除（未使用＋`.td-total` は将来の可読性事故の種）
- その他の未使用クラス（`.p-body` `.p-num` `.point-row` `.warn-box` `.flow` `.flow-item` `.formula` `.lead`）は、**1件ずつ widgets 側の定義有無を確認した上で**削除する。一括スクリプトは使わない
- **マークアップは一切変更しない**（未使用クラスの削除なので影響なし）

**A-3. 更新日表示の追加（9本）**

- 9本の `.meta` に「| 更新日：YYYY年M月D日」を追加し、既存の `dateModified` と一致させる
- **`dateModified` の値は変更しない。** 表示側を実態に合わせる方向で揃える（記事の中身を触っていないのに更新日を7/30に繰り上げるのは、検索エンジンに対して誠実でない）
- ただし A-1 で内容を拡充する `boki2-kessan.html` のみ、**JSON-LD と本文表示の両方を 2026-07-30 に更新**する（CLAUDE.md 2026-07-29ルール）

**A-4. 過度な断定表現の修正**

- `boki2-kotei-shisan-why.html`：「本番で絶対に間違えなくなりますよ」→「本番で間違えるリスクをぐっと下げられます」等
- 「試験で絶対引っかかる」→「試験で引っかかりやすい」
- 「絶対NG」（＝やってはいけない、の意）は**変更しない**

### 案B：`boki2-kessan.html` をハブ記事に純化する（今回は却下）

各決算整理事項の個別記事へ振り分ける役割に絞り、本文は薄くてよいと割り切る案。**GSCの検索クエリデータを見ないと判断できないため今回は却下。** A-1実施後にデータを見て再検討する。

### 案C：全部まとめて一括処理する（却下）

3件を1回のスクリプトで処理する案。**却下する。** CLAUDE.mdの2026-07-29の教訓（一括スクリプトで `dateModified` だけ更新し73ファイルの不一致を作った）が示す通り、**当社は一括処理で事故を起こす癖がある。** 分けて実施する。
