# 【稟議】LPモバイル48点の是正 — フォント非ブロック化とCLS対策

**起票日：** 2026年7月29日（実作業は7月30日未明）

**対象：** `index.html`

## 1. まず、私の報告が間違っていた

取締役に「パフォーマンス75点。速度は全部合格していて、落としているのはCLS単独」と報告した。**これはデスクトップの数字だった。**

| | モバイル（実測） | 私が報告した値 |
|---|---|---|
| パフォーマンス | **48** | 75 |
| LCP | **11.3秒** | 1.8秒 |
| FCP | **8.6秒** | 1.7秒 |
| Speed Index | **8.6秒** | 1.7秒 |
| CLS | 0.179 | 0.207 |
| TBT | 0ミリ秒 | 10ミリ秒 |

URLには `form_factor=mobile` を指定していたが、**JSでゲージを読んだときに取得した値がどちら側のものかを確かめなかった。** 「モバイルを指定したのだからモバイルの値だろう」で報告した。取締役がスクリーンショットを送ってくださらなければ、間違った前提のまま改修に入っていた。

**Googleはモバイルファーストインデックスなので、意味を持つのは48点の方である。** そして診断も逆だった。モバイルの主犯はCLSではなく、レンダリングブロック **8,910ミリ秒** である。

## 2. 犯人は日本語Webフォントだった

`<head>` でレンダリングをブロックしている外部リソースは1つしかない。

```
fonts.googleapis.com/css2?family=Cinzel:wght@700;900&family=M+PLUS+1:wght@400;500;700
```

`M PLUS 1` は日本語Webフォントである。日本語は数千字あるためラテン系と比べてファイルが桁違いに重い。PageSpeedのモバイル計測は「低速4Gスロットリング」で行われるため、ここで一気に詰まる。

**デスクトップでは同じブロックが1,500ミリ秒で済む。だからデスクトップは75点で、モバイルだけ48点に落ちる。** 数字の食い違いは、この一点で説明がつく。

### 副次的に見つかった無駄

```
AdSenseスクリプト : 1本読み込み
広告枠 <ins>      : 0個
```

**LPには広告枠が1つもないのに、AdSenseのライブラリだけを読み込んでいる。** 「使用していないJavaScript 255KiB」の主因はこれとGoogle Analyticsである。ただし現在AdSense審査中であり、外した場合の審査への影響が読めないため、**今回は手を付けない。**

## 3. CLSの犯人（モバイルでは主犯ではないが実在する）

### (a) アフィリエイトバナーのスロットに高さ予約がゼロ

`#lpBannerSlot` にJSでバナーを差し込んでいるが、このIDにCSS定義が一切なかった。バナー自身は `w:300,h:250` 等の寸法を持っているのに、**スロットは高さ0から突然300px超に膨らむ。** その下のコンテンツが全部押し下げられる。

### (b) ヒーローh1のタイピングアニメーション

```js
h1.innerHTML = '';                 // 一旦空にする
setTimeout(typeLine1, 400);        // 400ms後に1文字ずつ書き足す（80ms/字）
h1.appendChild(document.createElement('br'));  // 途中で改行を挿入 → 1行が2行になる
```

**約2秒間、h1の中身が変化し続ける。** しかも途中で `<br>` が入って1行→2行に変わるため、h1の高さが変わり、**その下の全要素がシフトする。** PageSpeedの「強制リフロー」の指摘とも一致する。

さらにSEO上の問題として、**HTMLソースのh1とユーザーが見るh1が別物**だった。

```
ソース : また三日坊主になる前に、仕組みを変えてみよう。
JS適用後: すべての勉強を、終わらない冒険に。
```

## 4. 実行した内容

### ① Google Fonts の非ブロック化（実行済み）

```html
<link rel="preload" as="style" href="...">
<link rel="stylesheet" href="..." media="print" onload="this.media='all'">
<noscript><link rel="stylesheet" href="..."></noscript>
```

`media="print"` にしておくとブラウザは描画に不要と判断してブロックせず、読み込み完了後に `all` へ切り替えて適用する。JS無効環境には `<noscript>` でフォールバックを用意した。

### ③ バナースロットの高さ予約（実行済み）

最大ケース（300px + gap16px + 50px＝366px）を `min-height` で確保し、`justify-content:center` を追加した。実際のバナーがこれより小さい場合は上下に均等な余白が出るが、コンテンツが飛ぶより遥かにましである。

### ④ h1の是正（実行済み）

- 静的HTMLのテキストを、JSが最終的に作る文言に合わせた（**SEOの不整合を解消**）
- `.hero h1` に `min-height:2.24em` を追加（`line-height:1.12 × 2行`）。**タイピング演出は残したまま、2行分の高さを最初から確保する**ので、アニメーション中に下のコンテンツが動かない

`em` 単位にしたのは、font-size が `clamp(38px,6.5vw,76px)` で可変のため。画面幅に関係なく常に正確に2行分を確保できる。

### ② 本文フォントのシステムフォント化（未実行・取締役判断が必要）

`M PLUS 1` をやめてシステムフォントにすれば、モバイルはさらに大幅に改善する。**ただしサイトの印象がはっきり変わる。** これは速度とデザインのトレードオフであり、CEOが単独で決めるべきではないと判断した。①③④の効果を再計測したうえで、必要なら改めて起案する。

## 5. CEO所見

**今日いちばん恥ずかしいのは、LP画像を95%削減した実績をココナラの看板にしようと提案したことだ。**

その提案をした時点で、モバイルは48点、LCPは11.3秒だった。画像を2,224KB→106KBにしたのに、である。**削るべき場所を削っていなかった。** 真のボトルネックはフォントで、画像最適化はモバイルの体感にほとんど寄与していなかった。商売の看板にする前に測ったのは、不幸中の幸いだった。

そして本件は、今日繰り返してきたミスの完成形でもある。**「width/heightを付ければCLSが直る」と信じて1,038枚に属性を付けたが、LPのCLSは0.179のまま。** 実際の犯人はJSの後入れ要素とタイピング演出だった。一般論に当てはめて作業し、実物を測らなかった。

一方で、この失敗そのものがサービスの核心になりうる。**「画像にwidth/heightを付ければCLSは直る」は多くの場合で嘘であり、実際はJSの後入れ要素が犯人であることが多い。** そしてデスクトップの数字を見て安心している人は多いはずだ。私自身が両方やらかした。この知見を持っている出品者は多くない。

**次にやること：** ①③④の効果を再計測する。デスクトップとモバイルを**必ず両方**記録し、レポートにはどちらの値かを明記する。
