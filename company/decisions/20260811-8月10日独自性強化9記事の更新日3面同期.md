## 2. ファクトチェック

### 事実確認の方法

git履歴（`9f6e311` / `266b025` / `7f25da3`、いずれも 2026-08-10）で各ファイルの `--numstat` を取得し、追加・削除行数と追加されたh2見出しを確認した。そのうえで、現在のHTML内の `"dateModified"`、本文の「更新日：」表示、sitemap.xml の `<lastmod>` を突合した。

**14記事のうち5記事（`boki2-ochita` / `boki2-roumuhi` / `boki3-seisanhyo` / `eiken` / `kenchiku`）は3面すべてが正しく `2026-08-10` になっている。** つまり手順自体は存在し、実行できている。9記事はその手順から漏れた。

### 「実質的更新」に該当するかの判定

監査手法メモには「機械的置換ではlastmodを動かすべきではない」という方針がある。今回の9件がこれに該当しないことを、以下で確認した。

- 5記事は**削除0行で16〜17行の追加**であり、新しいh2見出しを伴う。ペルソナ置換やタグ追加のような機械的変更ではなく、新規セクションの追加である
- `boki2.html` は18行追加・10行修正で、本文の記述そのものが変わっている
- `boki3-credit` / `boki3-genka` / `boki3-kabushiki` は行数こそ少ないが、コミットメッセージが示すとおり**事実整合の修正**であり、読者に届く情報の中身が変わっている

**すべて実質的更新に該当する。**

### Google側の扱いに関する裏付け

- Googleは sitemap の `lastmod` について「ページの内容が実質的に変更された最終日」を記載するよう求めており、正確な値であればクロールのスケジューリングに利用すると説明している（Google 検索セントラル「サイトマップの作成と送信」）
- 構造化データの `dateModified` は、記事系リッチリザルトにおいて更新日時のシグナルとして扱われる（Google 検索セントラル「記事（Article）の構造化データ」）
- 双方に共通するのは「**実際に更新したときに正しく申告する**」という一点である。今回の9記事は実際に更新しているにもかかわらず申告していないので、シグナルを取りこぼしている側にあたる

### CLAUDE.md との整合

CLAUDE.md「更新日を変更するときのルール（2026-07-29追加）」は、dateModified と本文表示の**2箇所セット更新**を必須としている。**今回の9記事はこのルールが守られていない。** 本稟議はルール違反の是正であり、新しい方針の提案ではない。

## 3. CEOジョブズの所見

**これは技術的な不備ではない。施策の自己否定である。**

8/10に何をやったかを思い出したい。AdSense不合格の原因として「独自性の不足」を特定し、それを埋めるために14記事へ独自の判断セクションを書き足した。**独自性を証明するための施策だった。**

その施策の結果が、いま `boki2-cvp.html` でどうなっているか。8/10に「数字を置き換えて確認する：損益分岐点と目標利益」という新しいセクションが入っている。しかし構造化データは `2026-06-26` と申告している。**サイト自身が「この記事は46日間、何も変わっていません」と言っている。** 書いた本人が「変わっていない」と署名しているのに、クローラーが優先的に見に来る理由はない。

厳しく見るべきは件数の内訳だ。**14件中5件は正しく直っている。** つまり「知らなかった」でも「難しかった」でもない。**同じ日に、同じ人が、同じ作業を、5回はやって9回はやらなかった。** これは手順の欠落ではなく、手順を最後まで回さなかったという運用の緩みである。

そしてCLAUDE.mdには、7月29日に追加した「更新日は2箇所セットで更新する」というルールが既にある。**ルールを明文化した12日後に、同じ種類の漏れが起きている。** 文書に書けば守られるという前提が成り立っていないことを、正面から認めるべきだ。だから本稟議には是正だけでなく、下の「再発防止」を必ずセットで通したい。

判断基準に照らす。

1. **収益に直結するか** — 間接的だが直結に近い。AdSense再審査に向けて独自コンテンツの評価を受けることが目的であり、そのコンテンツが「新しい」と認識されない状態は目的の達成を遅らせる
2. **見つけてもらえる状態に近づくか** — 明確にYES。実質更新の正しい申告はクロール優先度に効く
3. **ユーザーの人生を本当に変えるか** — 記事そのものは既に良くなっている。**これは「良くしたことを伝える」作業である。**

**足りない点を自分で挙げる。** この稟議は日付を直すだけで、根本原因である「手作業でのチェックリスト実行」には触れていない。日付を直せば今日は片付くが、次の一括作業でまた同じことが起きる。**再発防止をセットで通さなければ、この稟議は3回目・4回目が必ず来る。**

## 4. 再発防止（本稟議に含める）

CLAUDE.md「新規記事公開時のチェックリスト」と同じ形式で、**記事本文を変更したときのチェックリスト**を新設する。

```
記事の本文を変更したら（新規公開でなくても）、以下を必ず同時に更新する。

1. JSON-LD の "dateModified"
2. 本文に表示している「更新日：YYYY年M月D日」
3. sitemap.xml の <lastmod>

3つとも「実質的な本文変更があった日」で揃える。
機械的な一括置換（表記統一・タグ追加・ペルソナ置換など）では、3つとも動かさない。

複数記事をまとめて変更した場合は、変更した全ファイルについて
dateModified == 本文表示 == lastmod が成立するかをスクリプトで検算してから完了とする。
```

**検算をスクリプトで行うことを明記する点が肝である。** 目視での確認は、14件中9件を取りこぼした実績がある。
