## 1. 提案内容

サイトには「更新日」を名乗る場所が3つある。**どれを正とするかが決まっていないため、201記事のうち126記事で値が食い違っている。**

| 面 | 場所 | 見る相手 |
|---|---|---|
| ① | JSON-LD の `"dateModified"` | 検索エンジン・生成AI |
| ② | 本文に表示する「更新日：YYYY年M月D日」 | 読者 |
| ③ | sitemap.xml の `<lastmod>` | クローラー |

### 提案する原則（1行）

> **「実質的な本文変更があった日」を唯一の正とし、①②③をすべて同じ値で書く。機械的な一括置換では①②③とも動かさない。**

### 実行する是正（2段階）

**第1段階：矛盾が明白な19記事を直す（今回実行したい範囲）**

sitemap の lastmod が dateModified より**新しい**19記事。更新した記録がどこにも無いのに、sitemapだけが新しい日付を申告している。git履歴で実質更新の有無を1件ずつ確認し、

- 実質更新が**無い** → lastmod を dateModified の値まで**戻す**
- 実質更新が**ある** → 3面ともその日付に**揃える**

| ファイル | dateModified | lastmod | ズレ |
|---|---|---|---|
| `fp3-tax.html` | 2026-05-09 | 2026-07-10 | 62日 |
| `fp3-realestate.html` | 2026-05-09 | 2026-07-10 | 62日 |
| `fp3-inheritance.html` | 2026-05-09 | 2026-07-10 | 62日 |
| `boki2-zairyouhi.html` | 2026-05-09 | 2026-06-27 | 49日 |
| `boki3-progress.html` | 2026-05-10 | 2026-06-27 | 48日 |
| `boki2-yukashoken.html` | 2026-06-26 | 2026-07-09 | 13日 |
| `boki2-kobetsu-genka.html` | 2026-06-26 | 2026-07-09 | 13日 |
| `boki2-hyojun-genka.html` | 2026-06-26 | 2026-07-09 | 13日 |

**第2段階：lastmod が古い107件は「直さない」ことを明示的に決める**

こちらは大半が、7/26のペルソナ統一・7/29の更新日一括同期といった**機械的置換で dateModified だけが動いた**ものである。lastmod は正しく据え置かれている。

**したがって、直すべきは lastmod ではなく、過大申告された dateModified の側である。** ただし107記事の dateModified を過去に巻き戻す作業は、リスクに対して得るものが小さい。**「今後は機械的置換で dateModified を動かさない」というルールを立て、既存107件は現状のまま据え置く**ことを、記録に残る形で決定したい。

**あわせて、本文に「更新日」表示が無い25記事に表示を新設する**（第1段階の作業と同時に実施すれば追加コストはほぼゼロ）。

## 2. ファクトチェック

### 実測データ

全201記事について、JSON-LD の `dateModified` と sitemap.xml の `<lastmod>` を突合した。

| dateModified ≠ lastmod | **126件 / 201記事（63%）** |
| うち lastmod が古い | 107件 |

| 最大のズレ | 62日（fp3-tax / fp3-realestate / fp3-inheritance） |

### Google側の扱いに関する裏付け

- Googleは `lastmod` について「値が一貫して正確である場合にのみ利用する」と明言しており、**不正確な値を送り続けるサイトでは lastmod 自体を無視する**と説明している（Google 検索セントラル「サイトマップの `lastmod` について」）
- **これが最も重い事実である。** 63%が食い違い、19件は明白に誤っている現状は、「このサイトの lastmod は信用できない」という判定を受けても不思議ではない。その場合、8/10に正しく直した5記事の lastmod も、これから直す9記事の lastmod も、**まとめて無視される**

## 3. CEOジョブズの所見

**126件という数字に驚くべきではない。ルールが無いのだから、揃っている方が偶然である。**

7月29日の反省メモにこう書いてある。「一括更新のたびに不一致が積み増されていた」。あのときは①と②の不一致73件だった。それを直して、①と②は0件になった。**そして今、③との不一致が126件ある。2面を揃えても、3面目を決めていなかったから同じことが起きた。**

対症療法を2回繰り返した。3回目をやるつもりはない。**決めるのは「どれが正か」だけだ。** それさえ決まれば、①②③は同じ1つの値を書くだけの作業になり、食い違いようがなくなる。ルールが増えるのではなく、**判断が1つに減る。**

第2段階について、あえて「直さない」と提案する理由を書いておく。107記事の dateModified を7/29から6/27に巻き戻す作業は、機械的には可能だ。しかし**得られるのは「整合性が取れた」という自己満足だけで、読者にも検索にも何も起きない。** むしろ200近いファイルを一括で触ることで、また別の取りこぼしを生むリスクの方が大きい。**削るべきは作業であって、判断ではない。** 決定として明文化したうえで据え置く。

一方、第1段階の19件は**やらなければならない。** 特にfp3の3記事は62日のズレである。5月9日から一度も本文が変わっていない記事について、7月10日に更新したと申告している。これは間違いであり、間違いを放置する理由は無い。

判断基準に照らす。

1. **収益に直結するか** — 直結はしない。ただし lastmod が無視される状態になると、**今後のすべての更新申告が効かなくなる**。収益施策の土台を守る作業である
2. **見つけてもらえる状態に近づくか** — YES。lastmod の信頼性はクロール頻度に直結する
3. **ユーザーの人生を本当に変えるか** — 直接は変えない。**ただし「5月から更新していない記事を7月更新と表示する」のは、読者に対して誠実ではない。** 金額のルールで書いた「品質の問題ではなく信義の問題」と同じ種類の話である

**足りない点を自分で挙げる。** この稟議は、107件を据え置くという判断を含んでいる。整合性の観点では妥協である。**「63%が不一致のまま」という状態を、ルール制定を理由に正当化している側面がある**ことは認めておく。もし取締役が「全件揃えるべき」と判断するなら、その方が原理的には正しい。私は費用対効果でそれを採らなかった。

## 4. 追加する運用ルール（CLAUDE.md に記載）

```
## 更新日を扱うときのルール（3面同期・2026-08-11改訂）

サイトには「更新日」が3箇所ある。すべて「実質的な本文変更があった日」で揃える。

1. JSON-LD の "dateModified"
2. 本文に表示している「更新日：YYYY年M月D日」
3. sitemap.xml の <lastmod>

- 本文の中身が変わったとき → 3つとも変更日で更新する
- 表記統一・タグ追加・ペルソナ置換など機械的な置換 → 3つとも動かさない
- 複数ファイルを一括変更したら、3面が一致するかを必ずスクリプトで検算する

理由：Googleは lastmod が一貫して正確な場合にのみ利用し、不正確なサイトでは
無視すると明言している。1件の誤りが、正しい申告まで含めて無効化しうる。
```

既存の「更新日を変更するときのルール（2026-07-29追加）」を、このルールで置き換える（2箇所→3箇所に拡張）。
