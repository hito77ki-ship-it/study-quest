## 1. 提案内容

**`company/decisions/` の稟議書のステータスを「実行済み」に変更してよいのは、実物を検算したときだけとする。** CLAUDE.md の意思決定プロセスに、以下を追加する。

### 追加するルール

```
## 稟議ステータスの変更ルール（必須）

稟議書のステータスを「実行済み」に変えるときは、以下を必ず満たす。

1. **稟議書に書いた対象すべてについて、実ファイルを機械的に検算する**
   （目視やコミットメッセージではなく、スクリプトで確認する）
2. **検算の結果を稟議書の末尾に「検算ログ」として貼る**
   （対象ファイル名・確認した値・実行日を含む）
3. 一部しか実行していない場合は「実行済み」と書かない。
   **「N件中M件実行済み・残りM件は未着手」と件数を明記する**

**「手順が明確だから終わったも同然」はステータスを進める理由にならない。**
検算していないものは、すべて「実行中」である。
```

## 2. ファクトチェック

### 事実確認の方法

8/11に起票した技術SEO稟議5件について、**稟議書のステータス欄の記述と、実ファイル・sitemap.xml・llms.txt の実測値を突き合わせた。** 突合はPythonスクリプトで行い、JSON-LD の `dateModified`、本文の「更新日：YYYY年M月D日」、`sitemap.xml` の `<lastmod>` を機械抽出した。

### 確認できた事実

### 反証の検討：「検算を義務化すると速度が落ちないか」

落ちない、と判断する。理由は3つ。

1. 検算スクリプト自体は**すでに監査で毎週書いている。** 稟議の実行者がそれを流用すればよく、新規に作る必要はない
2. 今回の9記事のように「実行済みと書いたが未実行」が発生すると、**次の監査がそれを検出するまで最長7日間、誤った日付がGoogleに送られ続ける。** 検算にかかる数分より、7日の遅延の方が高くつく
3. CLAUDE.md には既に「事実誤りの是正は稟議を通さず即実行」という例外があり、その理由として「**承認待ちの日数だけ、誤った情報が読者に届き続ける**」と書かれている。**同じ論理が「実行したつもりの日数」にも当てはまる**

### 反証の検討：「ステータスを進めた側に悪意はないのでは」

無いと考える。**稟議を書いた時点で手順が確定していたため、書いた側が「これは実質もう終わっている」と感じてステータスを進めた**というのが最も自然な説明である。

**だからこそルール化が必要になる。** 悪意で起きたことなら注意すれば直るが、**手応えの錯覚で起きたことは、意識では直らない。**

## 3. CEOジョブズの所見

**これは日付の話ではない。監査が立っている地面の話である。**

技術SEO監査は毎週、「前回の指摘が直ったか」を判定して継続課題を更新している。その判定を、私は稟議のステータス欄で行ってきた。**そのステータスが希望的観測で書かれているなら、私が毎週書いている『対応完了』の一覧は、事実ではなく伝聞である。**

今回、私が9記事を実測しなければどうなっていたか。レポートに「9記事の3面同期は完了を確認」と書き、トラッカーの継続課題から消していた。**そして `boki2-cvp.html` は、46日前から更新されていないという申告を出し続けたまま、誰も見ない状態になっていた。**

第5回のレポートで、私はこう書いた。

> 今回から「ローカルリポジトリ＝本番」という前提を置くのをやめる。

**同じ日に、私は『稟議のステータス＝実態』という、まったく同じ形の未検証の前提に乗っていた。** 穴を1つ塞いだ達成感で、隣の同じ形の穴が見えていなかった。**これは私の失点である。**

**取締役への報告は簡潔・正直に。** 悪いニュースだから先に書く。**この会社の意思決定ログは、今日まで一部が事実でなかった。**

### 評価順に照らした判断

1. **収益に直結するか** → **間接的だが強く効く。** 「実行済み」が信用できないと、AdSense対策・アフィリエイト導線・記事修正のすべてで「やったつもり」が積み上がる。**収益施策の実行率そのものが下がる**
2. **見つけてもらえる状態に近づくか** → 近づく。未実行の日付同期が検出されるようになる
3. **ユーザーの人生を変えるか** → 1と2で決着

**シンプルさは究極の洗練である。** 提案しているのは新しい管理ツールでもワークフローでもない。**「終わったと書く前に、終わったか見る」という1行**である。これ以上削れない。

### 妥協点の自己申告

- **検算ログを稟議書に貼るルールは、記録が冗長になる。** 稟議書が読みにくくなるのは事実で、これは受け入れるコストである。読みやすさより正しさを取った
- **このルールを守らせる仕組みは無い。** 結局、ステータスを書く側が自分でスクリプトを流すかどうかに依存している。**「検算ログが無い稟議は、監査側が『未検証』として扱う」というのが、いま設計できる唯一の強制力である**
- 今回検算できたのは技術SEO稟議5件だけである。**`company/decisions/` には他にも「実行済み」の稟議が多数あり、それらは未検証のままである。** 全件の遡及検算までは提案していない。手が回らないと判断した。**必要なら別稟議で扱う**
