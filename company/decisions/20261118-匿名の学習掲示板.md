# 匿名の学習掲示板

決定日：2026年11月18日（Asia/Tokyo）

状態：画面・受付処理と隔離検証を準備。本番の保存先追加・配信は未実施。

今回の設計事項は5件。新しい掲示板だけが対象で、既存記事本文や学習記録の変更ではない。

## 本人の依頼と目的

本人は匿名掲示板の設置を希望し、1スレッド1,000件、20件ずつ表示、満了後の閲覧保持、続きへの導線、番号付き返信の案を採用した。資格学習で迷ったことを質問・共有できる場所を作る。利用需要・学習効果・検索流入や収益への効果は未検証。

## 実行する設計

1. 名前は任意で、未入力は「名無しさん」。個人のログインを要求せず、本文・任意名・受付日時を既存Supabaseに保存する。
2. 受付と公開を分ける。新規スレッド・返信は確認待ちとし、既存の管理者だけが公開・非公開・通報対応を行う。公開や回答の期日は約束しない。
3. 最初の投稿を1件目とし、承認時に番号を付ける。投稿数は保存側で1,000件以内に制約し、承認処理はスレッド行をロックする。非表示にしても番号と件数を維持する。
4. 一覧・本文は各20件ずつ取得する。返信番号のリンクから該当する20件へ移動できる。満了後は閲覧を残し、続きのスレッドは承認後に前後へリンクする。1スレッドに複数の有効な続きは作らない。
5. 投稿と通報の管理情報は専用の非公開スキーマに分離する。一般利用者にはDBの直接読み書き・管理RPCを許可せず、受付処理を経由する。二重送信は受付番号で照合する。匿名ブラウザごとの連投制限と全体の受付量・確認待ち件数の上限を設ける。

## 根拠

- [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys)：公開キーは利用者本人の識別ではない。管理操作は実際のAuthユーザーと既存のis_adminをサーバーで再確認する。既存の公開anon JWTを使用し、Edgeのverify_jwtは有効のままとする。
- [Supabase Edge authorization headers](https://supabase.com/docs/guides/functions/auth-headers)：ゲートウェイのJWT判定とアプリの管理者認可を分ける。
- [Supabase Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)：新しい全テーブルでRLSを有効にし、匿名・通常ログインへの直接権限を付与しない。
- [Googleのユーザー投稿に関する案内](https://support.google.com/adsense/answer/1355699?hl=ja)：投稿を公開前に確認する運用を採用。掲示板に広告枠は追加しない。

## 保存先への追加と確認が必要な範囲

実装は既存プロジェクトに新しい非公開スキーマと5テーブル、service_roleだけが呼べる受付用RPCを1つ、Edge Functionを1つ追加する案である。既存のテーブル・学習記録・コメント・アカウント・認証設定・契約・プラン・定期タスクは変更しない。

CLAUDE.mdの「ドメイン／外部サービス設定」等は包括委任の対象外で「都度の取締役指示を要する」という規則を適用する。本件の共有保存先・受付処理の本番追加は、その外部変更に当たると判断した。画面・SQL・受付・管理処理・検証済み差分を用意してから、この追加内容の確認を行う。一般的な実装判断を承認待ちにするものではない。

既存プロジェクトの現在のプランは読み取りでFreeと確認した。新規プロジェクト・有料化・追加契約は行わない。無料枠内での将来の使用量や運営負荷、料金が永久に発生しないことは保証しない。
