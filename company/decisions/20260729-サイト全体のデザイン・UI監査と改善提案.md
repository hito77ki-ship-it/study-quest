## 監査の方法

全211 HTMLファイルを対象に、以下を機械的に検査した。

- アクセシビリティ（alt属性、見出し階層、h1の重複、lang、viewport）
- パフォーマンス（画像容量、CLS要因、遅延読み込み、フォント読み込み）
- デザイン一貫性（nav/footer/パンくず/著者表記/更新日表記のゆらぎ）
- リンク整合性（内部リンク切れ、孤立ファイル）

**先に良い点を書いておく。** 以下は極めて良好な状態にあった。

- **リンク切れ：0件**（全内部リンクの参照先が実在）
- **alt属性：img 1,077件中、欠落はnoindexページの1件のみ**
- **h1：全ページちょうど1つ**（0個や重複が1件もない）
- **nav / footer：全記事に存在、欠落ゼロ**
- **lang / viewport：実記事ページは全て指定済み**
- `display=swap` は211ファイル全てに指定済み（FOIT対策済み）

土台の作りは想像よりずっと堅い。以下は「不備」というより**伸びしろ**の話として読んでほしい。

## 【優先度：最高】画像が重すぎる — Core Web Vitals 直撃

### 事実

| 項目 | 数値 |
|---|---|
| サイト内のPNG合計 | **32.9 MB**（182ファイル） |
| **LP（index.html）が読み込む画像の合計** | **2,224 KB** |
| `boki2-sogo-genka.html` の画像合計 | 827 KB |
| 200KB超の画像 | 50件 |

LPが読み込んでいるのはアプリのスクリーンショット3枚＋アイコンで、いずれも**実解像度1170×2532px**（iPhone実機解像度）。一方、CSS上の**表示幅は182〜260px**。**4.5〜6.4倍の過剰解像度**を配信している。

### 圧縮の実測結果（WebP変換）

| ファイル | 現状 | WebP変換後 | 削減率 |
|---|---|---|---|
| screenshots/screen1.png | 718 KB | 87 KB | **▲88%** |
| screenshots/screen2.png | 513 KB | 92 KB | **▲82%** |
| screenshots/screen3.png | 789 KB | 80 KB | **▲90%** |
| icons/app-icon.png | 204 KB | 52 KB | **▲75%** |

**LPだけで 2,224 KB → 約 311 KB（▲86%）** になる。さらに表示幅に合わせてリサイズすれば、もう一段軽くなる。

### なぜ最優先か

最優先目標は検索上位表示だ。Googleのランキング要因であるCore Web Vitalsのうち、LCP（最大コンテンツの描画）は画像の重さに直撃される。**しかもよりによって、一番重いのがLP（index.html）だ。**サイトの顔で2.2MBを配っている。モバイル回線のユーザーは、我々の作ったものを見る前に離脱している可能性がある。

正直に言えば、これは記事を1本書くよりも順位への影響が大きい可能性がある。記事の中身をどれだけ磨いても、表示される前に閉じられたら意味がない。

### 提案

- **案A（推奨）：** LP・記事で実際に使用中の画像をWebP変換し、`<picture>`要素でPNGフォールバック付きで配信。あわせてスクリーンショットを表示幅の2倍（Retina対応）にリサイズ
- **案B：** WebP変換のみ（リサイズなし）。作業量は少ないが効果はA未満
- **案C：** LPの4枚だけ先に対応し、効果をGSC/PageSpeedで測ってから横展開

## 【優先度：高】CLS（レイアウトシフト）対策が未実施

### 事実

- `<img>` 1,067件のうち、**width/height属性を持つのは 5件のみ**（99.5%が未指定）
- `loading="lazy"` の指定は **62件 / 1,067件**（5.8%）

width/heightが無いと、画像の読み込み完了まで高さが確定せず、読者が読んでいる最中に本文が飛ぶ。これがCLSで、こちらもCore Web Vitalsの指標。

記事は図解画像を多用する構成なので、影響は小さくない。

### 提案

全`<img>`にwidth/height属性を機械的に付与する（実ファイルから寸法を読んで自動挿入可能）。あわせてファーストビュー外の画像に`loading="lazy"`を付与する。**表示上の見た目は一切変わらない**、純粋な指標改善。

## CEOジョブズの所見

**率直に言って、この監査の結論は「デザインは悪くない、配信が雑」だ。**

取締役は「デザインやUIに不備がないか」と聞かれたが、見た目の設計思想——余白の取り方、緑のアクセント、ダークモードの作り込み、会話形式の導入——は一貫していて、個人開発のサイトとしては十分に整っている。alt属性がほぼ100%、リンク切れゼロ、h1の重複ゼロというのは、正直かなり良い。ここは自信を持っていい。

問題は見た目ではなく、**その見た目を届ける速度**だ。LPで2.2MBの画像を配っておいて「シンプルさは究極の洗練である」と言うのは、さすがに筋が通らない。しかも圧縮で86%落ちる。**落とせるのに落としていないだけ**だ。これは設計の失敗ではなく、単なる手抜かりであり、だからこそ直せば確実に効く。

「それはユーザーの人生を本当に変えるか？」で言えば、画像圧縮そのものは人生を変えない。だが**表示される前に離脱された記事は、どんな内容でもゼロだ。**我々は記事の中身に時間をかけてきたが、その中身が読まれる前提条件を整えていなかった。優先度を最高に置くのはそのためだ。

ひとつ自分たちに厳しく言っておくと、**孤立画像17MBと、使われていない1MB級の図解4枚は、作業の詰めの甘さの証拠だ。**図解を作ったのに記事に入れ忘れているなら、それは工数を捨てている。棚卸しは必要だ。

### 最優先目標との関係

- **検索上位表示：** Core Web Vitals（LCP・CLS）はランキング要因。画像最適化とwidth/height付与は直接的に効く。今回の提案で最も費用対効果が高い
- **Googleアドセンス合格：** 表示速度は審査の直接項目ではないが、ユーザー体験の質として間接的に効く。またCLSが大きいページは広告の誤クリックを誘発しやすく、ポリシー上も好ましくない
