## 1. 提案内容

**リポジトリの作業ツリーに36ファイルの未コミット変更が残っており、本番（study-quest.net）に反映されていない。** その中には llms.txt と robots.txt が含まれる。

**以下の2つを提案する。**

### (a) 未コミット36ファイルの内容を確認し、コミット・デプロイする

**私（CEO）はコミットを実行していない。監査タスクの制約により、発見と提案に徹している。** 取締役の承認後、以下の手順で処理したい。

1. `git diff` で36ファイルの変更内容を確認し、**意図した変更であることを1件ずつ確認する**
2. 意図しない変更・作業途中の変更が含まれていれば分離する
3. コミット・プッシュし、GitHub Pagesのデプロイ完了を確認する
4. **本番URLで llms.txt を開き、8記事が反映されていることを目視で確認する**

### (b) 「完了」の定義を変更する

```
作業の完了条件（2026-08-11 改訂）

以下をすべて満たしたときにのみ「完了」と呼ぶ。

1. ファイルを変更した
2. git commit した
3. push した
4. 本番URLで反映を確認した

1〜3のいずれかで止まっている状態は「作業中」であり、
company/reports/ や稟議の実行チェックリストに「完了」と書いてはならない。
```

**あわせて、監査タスク（技術SEO監査・記事品質監査）の冒頭に `git status` の確認を必須手順として追加する。**

## 3. CEOジョブズの所見

**この報告書は、私が嘘を書く一歩手前で止まったという記録でもある。**

前回の監査で「llms.txtに承認済み8記事が未反映」と書いた。今日ファイルを開いたら、8件とも入っていた。**普通ならそこで「解消」と書いて終わりだ。** 実際、私は今日のレポートの初稿にそう書いた。最後にリポジトリの状態を確認しなければ、取締役は「llms.txtは直った」と信じたまま次の週を迎えていた。

**監査を4回やって、一度も `git status` を見ていなかった。** 「ローカルリポジトリがデプロイ元だから、リポジトリを見れば本番がわかる」と書いてきた。**その前提が今日は成立していなかった。過去4回も成立していなかった可能性がある。** 監査手法メモにその前提を明記していたのに、前提が正しいかを確認する手順を入れていなかった。**書いた本人が確かめていない前提ほど危ういものはない。**

### より深い問題

36ファイルという数字を見てほしい。これは事故ではなく**日常**である。

我々は毎日、記事を直し、レポートを書き、稟議のチェックリストに「✅ 実行完了」と記入している。**その「完了」が何を指しているかを、誰も定義していなかった。** ファイルを保存した時点を完了と呼んでいた。

読者にとって、保存された変更は存在しない。**読者が今この瞬間に study-quest.net を開いて見るのは、昨日の23時59分のサイトである。** それ以降に我々がやった34記事分の作業は、読者の画面に一切現れていない。

**AdSense再審査を控えている状況で、これは致命的になりうる。** 審査に出すのは本番のURLだ。独自性を証明するために書いた本文が本番に無ければ、審査員が見るのは改善前のサイトである。**不合格の原因を直したつもりで、直す前のものを再提出する**ことになりかねない。

### 行動原則に照らす

行動原則の3番目は「**速く動き、正しく動く**」である。**我々は速く動いていた。** 8/10だけで14記事に独自性セクションを追加し、事実誤りを直し、llms.txtを更新した。速度は十分だ。

**問題は「正しく」の方だ。** 私はこれを「内容が正確であること」の意味で使ってきた。**今日、それが不十分だと分かった。届いていないものは、どれだけ正確でも正しくない。**

行動原則の5番目は「**取締役への報告は簡潔・正直に**」である。だから書く。**この見落としは私の責任である。** 監査タスクを設計したのは私で、`git status` を手順に入れなかったのも私だ。取締役は毎週「技術的に健全です」という報告を受け取っていたが、その報告は本番ではなくローカルについてのものだった。

### 判断基準に照らす

1. **収益に直結するか** — **YES、しかも最上位で。** アフィリエイト導線もAdSense審査も、本番に出ていなければ収益はゼロである。ローカルにある導線から売上は立たない
2. **見つけてもらえる状態に近づくか** — **YES。** 未コミットの改善は、クローラーから見て存在しない
3. **ユーザーの人生を本当に変えるか** — **前提条件。** 読めない記事は、どれだけ良くても人生を変えない

**5件の稟議のうち、これだけは今日中に処理したい。他の4件は、これが片付かなければ実行しても本番に出ない。**

### 足りない点を自分で挙げる

- **私は36ファイルの中身を1件ずつは確認していない。** 意図した変更なのか、作業途中で放置されたものなのかを判定していない。コミット前にその確認が必要であり、それは私ではなく変更を加えた作業の担当が行うべきである
- **`apple-lp/` ディレクトリが未追跡で残っている理由を把握していない。** 意図的に追跡外にしているのか、追加し忘れなのかが不明である。コミット前に判断が要る
- **本番URLを直接確認できないという制約は、今回も解消していない。** 社サンドボックスのallowlist制限により study-quest.net にアクセスできないため、「HEADの内容＝本番」という前提は残る。**push後にデプロイが失敗していた場合、私にはそれを検知する手段がない。** 取締役ご自身がブラウザで確認する手順を、完了条件の4番目として入れている理由はここにある
