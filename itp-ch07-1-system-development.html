ITパスポート 7-1 システム開発技術

図書館のグループ学習室を題材に、要件・設計・実装、単体から受入れまでのテスト、境界値と見積りを学びます。

要件を、動く予約機能に変える

第6章の大学図書館に、グループ学習室を予約する機能を追加します。人数は1〜4人とします。システム要件定義では、全体で必要な機能や性能を整理し、機器・ソフトウェア・人の運用で何を担うかを考えます。ソフトウェア要件定義では、人数の制限や空室の表示など、ソフトウェアが満たす条件を具体化します。

システム設計では、受付画面、認証、予約台帳をどう連携させるかを決めます。ソフトウェア設計では、例えば人数欄の見せ方や判定処理、画面と台帳で受け渡す項目を決めます。プログラミングではその設計をコードにします。設計の粒度や工程名は組織によって変わるため、問題文では決めようとしている対象に着目します。

導入時は、既存予約の移行件数や席番号を照合し、職員への案内や切替手順を用意します。妥当性確認では意図した利用環境で目的を達成できるかを見ます。予約を入力できても、閉館時の取り消しを職員が扱えないなら、実際の用途を満たすかを見直します。導入後の保守では、不具合修正や環境変更への対応などを行います。

テストは「どこまでつないで、何を確かめるか」で選ぶ

人数判定を単独で動かすのが単体テスト、画面と予約台帳などの連携を試すのが結合テストです。例えば画面が「4人」と送っても台帳に「1人」と保存される不具合は、判定処理の単体テストだけでは見つからないことがあります。システムテストでは、全体として機能や性能の要件を満たすかを確かめます。

運用テストでは、職員の交替、通信障害時の切替、問い合わせ対応など、現場の運用手順を試します。受入れテストでは、発注側などが合意した条件を満たすか確かめ、受入れを判断します。同じシナリオを使うことがあっても、確認の目的が違います。

テストの範囲と、テストデータの選び方を分ける

ブラックボックステストでは仕様と入出力に着目し、ホワイトボックステストではコードの分岐など内部の構造に着目します。人数判定の単体テストでも、入出力の仕様からデータを選ぶことができます。負荷テストでは想定した同時操作などで応答を調べ、回帰テストでは修正が以前の正常な動きに影響していないかを確認します。

同値分割では、同じ処理が期待される入力をグループに分けて代表を選びます。整数なら「0以下」「1〜4」「5以上」に分け、例えば0・2・5を使います。限界値分析（境界値分析）では結果が変わるところに注目します。次の図では0・1・4・5を試します。空欄や文字も送れる仕様なら、別の入力として試験に含めます。

見積りは、何を手がかりにしたかを確認する

人数欄を追加する見積りでは、画面変更に加えて、予約台帳や既存データ、テストも考えます。積算法では作業を小さく分け、それぞれの工数を足します。WBSは作業を分解して整理するために使えます。

見積り手法と、自習室予約で使う情報
手法手がかり
ファンクションポイント法入力、出力、照会、論理ファイルなどの機能を分類し、複雑さに応じた重みを付けてソフトウェア規模を見積もる。
類推見積法以前の予約変更機能の実績を参照し、今回追加する連携や難しさの違いを補正する。
プログラムステップ法見込まれるソースコードの行数などをもとに、規模や工数を推定する。
相対見積り既知の作業を基準に、別の作業の大きさを相対的に表す。ポイントはチーム内の尺度として使う。

規模、工数、暦上の日数は区別します。14人時の作業を2人が担当しても、設計が終わるまで実装を始められないなど、前後関係によって日程は変わります。

解説つきの自作例題6問

まず自分で選び、解答を開いて、判断に使った条件を確かめます。

第1問　画面と台帳をどうつなぐか

受付画面、認証、台帳をどのように分け、どの項目をやり取りするか検討します。主にどの工程ですか。

  1. 保守
  2. システム設計
  3. 運用テスト
  4. 受入れテスト
第1問の解答と解説

イ　システム設計

構成要素とその連携の具体化はシステム設計です。運用テストは、できたものを現場の手順で使えるか確かめる段階です。

第2問　判定は合うのに、人数が台帳に入らない

人数判定の単体テストは成功しました。画面で4人を選んだとき、台帳にも4人が記録されるかを重点的に確かめます。何のテストですか。

  1. 人数判定だけの単体テスト
  2. 受入れテストだけ
  3. 画面と台帳の結合テスト
  4. コードレビュー
第2問の解答と解説

ウ　画面と台帳の結合テスト

二つの部分をつなぎ、送信値が台帳に渡るかを確かめるので結合テストです。画面の値と保存結果を突き合わせます。

第3問　受付と拒否の境目を選ぶ

予約人数は整数で1〜4人だけ有効です。両端と、そのすぐ外側を一つずつ確認する組合せはどれですか。

  1. 0・1・4・5
  2. 1・2・3・4
  3. 0・2・5・6
  4. 1・3・4・6
第3問の解答と解説

ア　0・1・4・5

下限は0と1、上限は4と5で判定が切り替わります。すべて有効な1・2・3・4だけでは、範囲外が拒否されるか分かりません。

第4問　上限の修正後に取消を確かめる

人数の判定を直したあと、以前できていた予約取消と空席表示も同じように動くか確かめます。目的はどれですか。

  1. 負荷テスト
  2. コードレビュー
  3. デバッグ
  4. 回帰テスト
第4問の解答と解説

エ　回帰テスト

変更が既存の機能を壊していないか確認するので回帰テストです。人数上限の不具合そのものが直ったかも、別途、同じ入力で再確認します。

第5問　工数を足し上げる

設計4人時、実装6人時、テスト4人時と見積もりました。記述のうち適切なものはどれですか。

  1. 総工数は10人時
  2. 総工数は14人時。暦上の所要時間は作業の前後関係も見る
  3. 2人なら必ず7時間で終わる
  4. 人時はソースコードの行数を表す
第5問の解答と解説

イ　総工数は14人時。暦上の所要時間は作業の前後関係も見る

4＋6＋4＝14人時です。実装が設計に依存するなど、同時に進められない作業もあるため、人数で割るだけでは日程は決まりません。

第6問　利用者から見える機能で規模を見積もる

入出力や照会などを分類し、複雑さの重みを使って規模を見積もる手法はどれですか。

  1. ファンクションポイント法
  2. プログラムステップ法
  3. 境界値分析
  4. コードレビュー
第6問の解答と解説

ア　ファンクションポイント法

利用者に提供する機能を手がかりにするのがファンクションポイント法です。プログラムステップ法は行数などから考えます。

方式設計・保守・品質を同じシステムで見分ける

学習室の予約が集中する時間に、窓口で代理受付もできるようにします。誰が何を担うかを決める場面、出来上がったものを試す場面、公開後に改修する場面を区別します。

用語を場面と結び付ける
用語意味と使う場面
システム方式設計システム全体の機能を機器・ソフトウェア・人の作業などにどう割り当てるかを決める。例えば緊急時の本人確認だけ窓口で行う。
コーディング・結合・妥当性確認設計をプログラムにする。結合では部品間の動きを確かめ、妥当性確認では実際の利用目的を満たすかを確かめる。
機能テスト・性能テスト・例外テスト取消できるか、混雑時にも応答するか、想定外の入力や通信途絶を扱えるか、目的ごとに試す。
回帰テスト・バグ管理図変更後に以前の機能が崩れていないかを確認する。バグ管理図では発見・修正の件数などの推移を見て、試験範囲も併せて判断する。
保守プロセス稼働中のシステムの障害修正、環境の変化への対応、性能の改善などの変更を管理する。日々の予約を受け付ける運用と区別する。
ソフトウェア品質特性・積み上げ法品質を機能、性能、保守のしやすさなどに分けて見る。見積りの積み上げ法は作業ごとの工数を見積もって合計する。

補足の自作例題

予約は取れますが、公開後に一覧が重くなりました。データの取得処理を直して応答を改善する活動は何ですか。また、改修後に取消が動くかを見るテストは何ですか。

解答と考え方を開く

処理の改善は保守です。別の既存機能が改修の影響を受けていないか確かめるのは回帰テストです。
